   
• 可以，当前 CPU 8-way fused 版本还有三类优化空间：数据结构扁平化、SIMD 化、并行 reduce 优化。优先级我建议按这个顺序做。

  1. 扁平化 pair_groups

  现在热路径里每次算距离会访问：

  head_pair_groups[head][stage]

  这是 vector<vector<vector<int32_t>>>，会有多层指针跳转。虽然每个 subspace 的 pair 数不大，但这个访问发生在：

  iter * heads * token_tiles * tokens * 8 * k

  频率很高。

  更好的做法是在 executor 初始化时转成连续数组：

  pair_offsets: [heads, 8 + 1]
  pair_ids:     [total_pairs]
  sub_dims:     [heads, 8]

  或者固定 8-way 版本：

  pair_ids:  [heads, 8, max_pairs]
  pair_lens: [heads, 8]

  热路径就变成：

  const int32_t* pairs = pair_ids + ((head * 8 + stage) * max_pairs);
  int32_t pair_len = pair_lens[head * 8 + stage];

  好处：

  - 少多层 vector 解引用。
  - 更利于编译器优化。
  - 后面 SIMD gather/手动展开更容易做。
  - subspace 维度可变仍然支持，因为 pair_len 每个 head/stage 都不同。

  2. 扁平化 labels / centroids

  现在输出仍是：

  result->per_head_labels_m[head][stage][token]
  result->per_head_centroids_m[head][stage]

  为了兼容上层结构可以最终填回这个格式，但热路径内部最好用扁平 buffer：

  labels_flat:    [heads, 8, tokens]
  centroid_flat:  [heads, 8, max_k, max_sub_dim]
  centroid_masks 或 sub_dims 标记有效长度

  热路径里：

  int32_t* labels = labels_flat.data()
      + (head * 8 + stage) * n_tokens;

  float* centroids = centroid_flat.data()
      + ((head * 8 + stage) * max_k) * max_sub_dim;

  好处：

  - 连续内存。
  - 减少 vector 访问。
  - labels 写入更 cache-friendly。
  - reduction buffer 和 centroid buffer 可以共享同一套 offset 计算。

  最终再把 flat buffer 拷贝/移动到 KmeansResult，这一步不是热路径。

  3. SIMD 距离计算

  当前每个 subspace 距离是按 RoPE pair gather：

  for pair in pairs:
      diff0 = token[pair] - centroid[offset]
      diff1 = token[pair + half] - centroid[offset + 1]

  因为 pair id 是自适应划分，不一定连续，所以不能直接用普通 contiguous AVX load。但有几种方案。

  第一种，低风险：对 small sub_dim 手动展开。

  很多 subspace 可能是 sub_dim = 16 或类似小维度。可以按 pair_len 做专门函数：

  distance_pairs_4
  distance_pairs_8
  distance_pairs_16
  generic fallback

  减少循环控制和 offset 更新。

  第二种，使用 AVX2 gather。

  token 的两个维度来自非连续位置，可以预先构造 dim ids：

  dim_ids: [heads, 8, max_sub_dim]

  然后用 _mm256_i32gather_ps 从 token_fp32 gather 8 个 float：

  __m256 x = _mm256_i32gather_ps(token_fp32, idx, 4);
  __m256 c = _mm256_loadu_ps(centroid + d);
  diff = x - c;
  sum += diff * diff;

  这要求 dim_ids 是连续 int32，刚好和扁平化一起做。

  注意：AVX2 gather 不一定总比标量快，尤其维度很小、访问都在 L1 时。要 benchmark。

  第三种，更激进：tile 内预投影。

  当前 tile 已经有完整 [tile_tokens, head_dim]。可以为每个 (head, stage) 在 tile 内生成连续 subspace view：

  tile_subspace: [tile_tokens, sub_dim]

  然后距离计算变成 contiguous AVX load。

  但这会重新引入一点 copy。是否值得取决于：

  k * iter 是否足够大

  如果每个 subspace 要和很多 centroid 比较，预投影一次、后面重复用 contiguous SIMD 可能更划算。

  4. SIMD fp16/bf16 转换

  现在 tile 转换是逐元素：

  for d:
    fp16_to_fp32(raw)

  可以改成向量化转换。

  如果 CPU 支持 F16C：

  _mm256_cvtph_ps

  一次把 8 个 fp16 转 fp32。

  bf16 可以用 AVX2：

  uint16 -> uint32 << 16 -> reinterpret float

  也能批量做。

  注意：这只优化 tile load 阶段。kmeans 主耗时通常还是 distance + reduction，所以优先级低于 pair/centroid 扁平化和距离 SIMD。

  5. Reduction 优化

  当前是：

  thread_sums[thread][task][k][sub_dim]
  thread_counts[thread][task][k]
  reduce all threads into global

  问题是线程多时，reduce 会扫一遍比较大的 buffer。

  可以优化成：

  - 每个 thread 只为它实际处理过的 (head, stage) 分配 accumulator。
  - 或按 head 分组 reduce，避免所有 thread 扫全部 task。
  - 或 OpenMP task-local + tree reduce。

  但这个优化要小心，复杂度会上升。建议先 profile，看 reduce 是否真的占比高。

  6. 最推荐的实施顺序

  我建议下一步这样做：

  1. 扁平化 pair_groups 和 dim_ids。
  2. 扁平化 labels / centroids / sums / counts 热路径 buffer。
  3. 把距离函数改成基于 dim_ids 的连续接口：

     distance_dim_ids(token_fp32, dim_ids, dim_count, centroid)

  4. 加 AVX2 gather 版本，但保留 scalar fallback。
  5. 再看是否需要 tile 内预投影。
  6. 最后才优化 fp16/bf16 SIMD 转换和 reduction。

  最关键的是前两步。它们不改变算法，只把热路径从“多层 vector + 可变结构访问”改成“连续数组 + offset”，收益稳定，也为 SIMD 铺路。
   
   当前问题

  现在 CPU 路径是：

  for head:
    for subspace in 8:
      复制 subvec[token, sub_dim]
      对这个 subspace 单独跑 kmeans

  问题有几个：

  - subvecs[head*8] 会额外写一遍大内存。
  - 每个 subspace 独立扫 token，8 个 subspace 会重复读同一批 KV。
  - 外层 task 很碎，内层又 OpenMP，容易造成线程调度开销。
  - fp16/bf16 先整层转 fp32，内存带宽压力很大。
  - CPU 和 GPU compact 语义虽然现在已统一，但 kmeans 阶段的数据流还不统一。

  目标设计

  新 CPU executor 专门服务 8-way learned partition：

  kmeans_execute_8way_fused(
      keys_u16,
      kv_heads,
      n_tokens,
      head_dim,
      k_values[8],
      head_pair_groups,
      dtype,
      worker_threads,
      runtime_config,
      sequence_major
  )

  输出仍然填充现有 KmeansResult：

  per_head_labels_m[head][8][token]
  per_head_centroids_m[head][8][k * sub_dim]
  per_head_subspace_dims[head][8]

  这样上层 reorganize_from_kmeans_m() 和 search metadata 还能继续复用。

  核心并行方式

  不要并行 (head, subspace)，而是并行 (head, token_tile)。

  每一轮 Lloyd iteration：

  parallel over head-token tiles:
    读取一个 head 的一段 tokens
    每个 token 只加载一次 head_dim
    对 8 个 subspace 分别算 nearest centroid
    写 labels[head][subspace][token]
    累加 thread-local sums/counts
  reduce thread-local accumulators
  update 8-way centroids

  这样一个 token 的数据被读进 CPU cache 后，8 个 subspace 都顺手处理掉。

  内存布局

  建议内部用扁平布局，不要 vector<vector<vector>> 作为热路径结构：

  labels:    [heads, 8, tokens] int32
  centroids: [heads, 8, max_k, max_sub_dim] float
  sums:      [threads, heads, 8, max_k, max_sub_dim] float
  counts:    [threads, heads, 8, max_k] int32

  最终再把扁平结果填回 KmeansResult 的 vector 结构。热路径不要反复走多层 vector 间接寻址。

  fp16/bf16 处理

  不要整层 keys_fp32 = fp32(keys_u16)。

  更合适：

  每个 thread 维护 tile_fp32 buffer:
    [tile_tokens, head_dim]

  处理一个 (head, token_tile) 时：

  1. 从 fp16/bf16 读入 tile。
  2. 转成 fp32 到 thread-local buffer。
  3. 8 个 subspace assignment 共用这份 fp32 tile。
  4. tile 处理完丢弃。

  这会把额外 fp32 内存从：

  kv_heads * tokens * head_dim

  降到：

  threads * tile_tokens * head_dim

  初始化

  第一版可以保持确定性和简单：

  - 每个 head/subspace 仍然做 kmeans++。
  - 但不要构造 subvec。
  - kmeans++ 距离计算直接从原始 KV + pair group gather。
  - min_dists 使用 [head][8][tokens] 或每个 task 临时 buffer。

  如果想更快，后续可以换成 sampled kmeans++ 或固定 stride 初始化，但第一版不建议同时改算法行为。

  compact 阶段

  CPU compact 应该继续和 GPU 对齐：

  for token:
    code = pack(labels[0..7])
  sort unique active codes
  compact_id = lower_bound(active_codes, code)
  cluster_offsets / compact_codes / final_labels

  为什么这更适配 8-way

  因为 8 个 subspace 是同一个 token 的 8 个投影，不是 8 个完全独立任务。最佳 CPU 数据流应该利用这一点：

  load token once
  convert once
  visit 8 subspaces
  accumulate 8 reductions

  而不是：

  copy subspace 0 and scan all tokens
  copy subspace 1 and scan all tokens
  ...
  copy subspace 7 and scan all tokens

  实现顺序

  1. 新增 KmeansExecutor8WayFused，只服务 stages == 8。
  2. 在 kmeans_execute_m() 里：
      - 如果 head_pair_groups.size == 8，走 fused executor。
      - 否则保留旧 M-way executor，避免破坏其它路径。
  3. 先保留 kmeans++ 行为，确保结果语义一致。
  4. 去掉 8-way CPU path 的 subvecs 分配。
  5. 用 thread-local tile fp32 buffer 替代全量 fp32 buffer。
  6. 最后再考虑进一步优化初始化和 Lloyd update。
  
  核心结论

  当前数据流里最不合理的地方有三个：

  1. library/AdaptiveIMI/cpp_extensions/cuda/hybrid_8way_builder.cu:685 分配了：
     dense_counts / dense_offsets / dense_cursors / active_scan / code_to_compact = [rows, dense_code_space]

     这里 dense_code_space = k1*k2*...*k8。实际 active clusters 最多只有 T，但代码按整个组合空间扫。k_values 一变大，显存和时间都会爆。
  2. library/AdaptiveIMI/cpp_extensions/src/hybrid_8way_bindings.cpp:22 的 CPU reorg 逻辑只是按 rows 并行。rows=batch*kv_heads 通常只有 8/16，所以 CPU 利用率低是正常的。
     正确做法应该按 row-token tile 并行，而不是按 head 并行。
  3. GPU path 和 CPU path 的“重组”概念分裂了。CPU path 在 library/AdaptiveIMI/cpp_extensions/src/reorganize_core.cpp:406 里从 labels 算 reorder，再 copy；GPU path 在
     hybrid_8way_bindings.cpp 里用 token_ids_by_cluster copy。底层 KV copy 应该合成一个共享 C++ primitive。

  正确的数据流

  GPU builder 应该只做这些：

  - GPU 上跑 8-way kmeans，得到 labels[row, 8, token]
  - GPU 上把每个 token 的 8-way labels pack 成一个 code
  - GPU 上按实际 token 的 code 做 compact，不扫 dense code space
  - GPU 输出：
      - CPU reorg 必需：token_ids_by_cluster
      - flat decode 必需：cluster_counts / cluster_sizes / cluster_offsets / full_centroids
      - subspace_rerank 额外必需：subspace_centroids / subspace_centroid_masks / subspace_dim_ids / subspace_dim_masks / compact_codes

  不应该长期保留：

  - token_labels
  - _labels_cuda
  - CPU copy 的 search metadata
  - head_indices / batch_indices / local_head_indices D2H，这些可以由 row index 推出来
  - dense_code_space 参数

  CUDA dense workspace 怎么改

  最佳方案不是 hash，而是 segmented radix sort。原因是它能保持和旧 dense code 顺序一致，验证成本低，而且复杂度变成 O(rows * T)，不再依赖 product(k_values)。

  替换流程：

  1. pack_codes_kernel
      - 输入 labels[row, 8, token]
      - 输出 codes[row, token] = packed uint64 code
      - 输出 token_ids[row, token] = token
      - padding token 设成 UINT64_MAX
  2. cub::DeviceSegmentedRadixSort::SortPairs
      - 每个 row 一个 segment
      - sort codes，values 是 token_ids
      - 得到 code 分组后的 token 顺序
  3. mark_cluster_starts_kernel
      - start_flag[pos] = code[pos] != code[pos-1]
      - padding 不算 cluster
  4. segmented exclusive scan start_flag
      - 得到每个 token 所属 compact cluster id
  5. fill_compact_metadata_kernel
      - 写 token_ids_by_cluster[row, pos]
      - 写 cluster_offsets[row, cluster]
      - 写 cluster_counts[row]
      - 如启用 subspace_rerank，写 compact_codes[row, cluster, 8]
  6. finalize_cluster_sizes_kernel
      - cluster_sizes[c] = offsets[c+1] - offsets[c]
      - tail offsets 填 token_count
  7. compute_true_full_centroids_kernel
      - 这部分可以继续用现有逻辑

  这样可以删掉这些 kernel / tensor：

  - initialize_dense_workspaces_kernel
  - count_dense_codes_kernel
  - dense_active_flags_kernel
  - finalize_dense_compact_kernel
  - scatter_dense_reverse_index_kernel
  - dense_counts
  - dense_offsets
  - dense_cursors
  - active_scan
  - code_to_compact

  CPU C++ reorg 应该怎么写

  CPU reorg 不应该重新理解 cluster，也不应该有 fallback。它只做一件事：

  > 按 GPU 产出的 token_ids_by_cluster，把 raw CPU KV copy 到 list buffer。

  但底层 copy 要改成 shared primitive：

  - 新增 reorder_core.{hpp,cpp}
  - 暴露一个内部函数，例如：
    copy_kv_by_token_order_rows(...)
  - hybrid_8way_bindings.cpp 调它
  - reorganize_core.cpp::reorganize_single_head 也调它
  - 删除两套重复 memcpy loop

  并行方式改成 token tile：

  tasks = rows * ceil(max_tokens / tokens_per_task)

  parallel_for(tasks):
      row = task / tasks_per_row
      tile = task % tasks_per_row
      dst range = tile token range
      for dst in range:
          src = token_ids_by_cluster[row, dst]
          memcpy key
          memcpy value

  这样 CPU 核心数才能吃满。现在按 row 并行的实现天然吃不满。

  我建议的实现顺序

  1. 先做共享 CPU C++ reorg primitive，按 token tile 并行，删掉 duplicate copy loop。
  2. 清理 metadata contract：CPU 只接收 reorg 和 flat decode 必需 metadata；search metadata 默认只留 GPU。
  3. 改 CUDA compact 阶段为 segmented sort，完全删除 [rows, dense_code_space] workspace。
  4. 修改 Python binding，去掉 dense_code_space 参数，去掉 token_labels/_labels_cuda 返回。
  5. 加 small-case 对照测试：新 sort compact 输出要和旧 dense path 的 cluster_counts / offsets / sizes / token_ids / compact_codes 一致。

  这个方向才是和当前 8-way 算法最适配的。只修 Python metadata 或只搬 CPU copy 位置，解决不了根因。
